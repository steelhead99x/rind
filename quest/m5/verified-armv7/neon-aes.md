# [L] armv7's NEON AES is proven

## Goal

aws-lc's `bsaes-armv7` and `vpaes-armv7` NEON routines, which armv7 runs for AES and AES-GCM without the crypto extension, are proven on the AArch32 model against FIPS 197, and composed in Lean with `Rind/Armv7/GhashNeon.lean`'s NEON GHASH and the Rust proofs of rind's AES-GCM, so those operations earn the ✓ on that tier.

## Plan

Decided 2026-11-18 (maintainer, [kixel-ai/rind#619](https://github.com/kixel-ai/rind/pull/619#issuecomment-6994276361)): the proof of the NEON AES switch, which [kixel-ai/rind#913](https://github.com/kixel-ai/rind/pull/913) made, goes under this epic.

- Route: as [armv7's assembly](/quest/m5/verified-armv7/assembly.md) proves the other routines, against the FIPS 197 and SP 800-38D specs the x86_64 and aarch64 quests write, composed with the Rust proofs of rind's AES-GCM and mode glue.
- AES-GCM above `AesGcm` is proven on any `GcmReady` key (`Rind/Armv7/AesGcm.lean`): this tier proves that `AesGcm::new` on a CPU with NEON but not the crypto extension keys `Neon` with `PartsFor` its `Arm`, and extends `RunsAesGcm` and `aes_gcm_new_spec` to it.
- NEON GHASH is done: `Rind/Armv7/GhashNeon.lean` restates [kixel-ai/rind#1088](https://github.com/kixel-ai/rind/pull/1088)'s HOL Light theorems and proves `neon_new_ghashFor`, the `GhashFor` that `PartsFor`'s table field asks. What remains is `NeonKey`'s `encrypt_block` and `ctr32`, then `PartsFor` for `Arm<NeonKey, NeonTable>`.
- `vpaes_encrypt` is proven ([kixel-ai/rind#1148](https://github.com/kixel-ai/rind/pull/1148)): `proofs/hol-light/armv7/vpaes_encrypt.ml`'s `VPAES_ENCRYPT_FIPS197_SUBROUTINE_CORRECT` stores `word_bytereverse (aes_fips_cipher n (word_bytereverse x) ks)` for n of 9, 11, or 13, given round keys in `vpaes_schedule n ks` form, and `aes_fips_cipher` 9 and 13 are `aes128_cipher` and `aes256_cipher`. `admin/prove` extracts `_vpaes_consts..vpaes_encrypt` and resolves same-section `R_ARM_CALL`s; the fork's step keeps `aarch32_tbl` folded until its index is a numeral (`AARCH32_TBL_CONV`), and the proof folds each round's intermediate values (`VP_FOLD_TAC`) and splits the loop on `(i + 1) MOD 4`, so the whole file checks in about 110 s compiled. Its lemmas (`vpaes_state`, `vpaes_key`, `VPAES_ROUND`, `VPAES_CIPHER`) are what the remaining vpaes routines reuse.
- The math as proven: T is `vpaes_tb` (`ipt`'s lookups, GF(2)-linear, `T(0x63) = 0x5b`), the state after i middle rounds `tbl(T(s_i), sr[(-i) mod 4])`, the keys `K_0 = T(k_0)`, `K_j = tbl(T(mix3(k_j)) ^ 0x5b, sr[(-j) mod 4])` for 1 to n, and the last `tbl(k_{n+1} ^ 0x63, sr[(n+1) mod 4])`, which equals its inverse permutation only because n is odd. Each round is a lane-wise `BITBLAST_TAC` once the S-box outputs are atoms (`VPAES_SB1_BYTE`, `VPAES_SB2_BYTE`, `VPAES_SBO_BYTE`, 256 cases each).
- Remaining for vpaes: `vpaes_set_encrypt_key` writing `vpaes_schedule n (aes_key_expansion key)` (the fork's `common/fips197.ml` has AES-128 and AES-256 key expansion only; AES-192 needs one), `vpaes_ctr32_encrypt_blocks` (the same core in a loop), and `vpaes_encrypt_key_to_bsaes`; `vpaes_decrypt` and `vpaes_set_decrypt_key` only if a proven path calls them.
- Bitsliced AES (`bsaes_ctr32_encrypt_blocks`, from eight blocks on) needs a proof that its bit-sliced S-box circuit computes the S-box; look for an existing one (s2n-bignum, Fiat, Jasmin) before writing it. `vpaes_encrypt.ml`'s byte lemmas give the S-box as `aes_sub_byte`, so a circuit lemma per output bit against `aes_sbox_table` is one route.
- Lessons from the GHASH proof: a NEON macro's leftover terms in scratch registers make each later step slower, so rename them to fresh variables between macros (its `FORGET_TAC`); name each Q register's initial value before a D-half write; and `BITBLAST_RULE` proves linear identities over 400 variables in seconds once nonlinear pieces are generalized to atoms.
