# [XL] armv7's assembly is proven

## Goal

Every assembly routine armv7 runs is proven on the AArch32 model in `thirdparty/s2n-bignum/aarch32/`, so SHA-2, SHA-1, ChaCha20-Poly1305, AES and AES-GCM with the crypto extension, ML-KEM, and RSA earn the ✓ on armv7.

## Plan

Runs, each in `low/arm/`, in rough order of use:

- aws-lc's `sha_armv4`: SHA-1 with the crypto extension, SHA-256 and SHA-1 on NEON and without, and SHA-512 without NEON. Proven: SHA-256 with the crypto extension ([kixel-ai/rind#1129](https://github.com/kixel-ai/rind/pull/1129), `proofs/hol-light/armv7/sha256_armv4.ml`), whose Lean axiom restating `SHA256_BLOCK_DATA_ORDER_HW_SUBROUTINE_CORRECT` for the crypto-extension call alone in `low::arm::sha_armv4::sha256_compress_blocks` remains, as `Rind/X86_64/Sha256Shaext.lean` restates x86_64's, composed through that function's empty-input return and CPU dispatch, and with the hash proofs once armv7's translation reaches them; and SHA-512 on NEON (`proofs/hol-light/armv7/sha512_armv4.ml`, restated about `compress_neon` in `Rind/Armv7/Sha512Entry.lean`, so `RunsSha512` takes NEON). Proving `sha512_block_data_order_nohw` the same way, restated about `compress_nohw`, drops NEON from `RunsSha512` and earns armv7's Ed25519 its ✓ ([armv7's X25519 and Ed25519](/quest/m5/verified-armv7/curve25519.md)). Its 80 rounds run as a loop of 32-bit halves, each round storing its state words to a window of stack slots that moves down 8 bytes, and the schedule computed in the same slots, so it needs a loop invariant over the round's slots and lemmas joining each 32-bit add-with-carry pair into a 64-bit add;
- aws-lc's `chacha-armv4` (integer below 192 bytes, NEON above) and its NEON Poly1305, under rind's port of `poly1305_arm.c`;
- aws-lc's `aesv8-armx` and `ghashv8-armx`, under rind's AES-GCM composition, which is proven above `AesGcm` on any `GcmReady` key (`Rind/Armv7/AesGcm.lean`): this tier proves that `AesGcm::new` with the crypto extension keys `Hw` with `PartsFor` its `Arm`, and extends `RunsAesGcm` and `aes_gcm_new_spec` to it;
- OpenSSL's `keccak1600-armv4`, integer and NEON, under ML-KEM and SHA-3;
- OpenSSL's `ecp_nistz256-armv4` (`ecp_nistz256_mul_mont`, `_sqr_mont`, `_add`, and `_sub`), under P-256's field arithmetic and so its ECDH and ECDSA;
- aws-lc's `bn_mul8x_mont_neon` and `bn_mul_mont_nohw`, under RSA.

The model, which [its `RIND.md`](/thirdparty/s2n-bignum/RIND.md#rinds-aarch32-model) describes, decodes every integer, Advanced SIMD, and crypto-extension instruction of these routines as rind's release build for `armv7-unknown-linux-gnueabihf` emits them. When a routine changes, or a `.byte` or `.inst` spelling hides one, a word that no longer decodes gets no theorem, so its proof fails there: add the instruction to the model with cosimulation cases, in this quest's PR. A subroutine's theorem assumes `aarch32_bx_target` of its return address, aligned to four bytes for an A32 caller or with bit 0 set for a T32 one, so it holds for every armv7 target, as `proofs/hol-light/armv7/ct_compare_*.ml`'s do. `AARCH32_ADD_RETURN_NOSTACK_TAC` and `AARCH32_ADD_RETURN_STACK_TAC` take it from there, the second with `aligned 4` of SP too, counting a `vstmdb sp!, {d8-d15}` after the `push` in its prologue and naming Q4-Q7 in its `qreglist`, with `aarch32_nowrap` of its stack frame and of each buffer an access reaches that is more than one byte at an address not known aligned to four, such as a `VLD1.16` lane, or a transfer of more than one word, since a transfer that would run past 0xffffffff leaves the model. A conditional load or store records an access of no bytes when skipped, which `memaccess_inbounds` accepts only if the theorem lists a range of the access's kind, readable for a load and writable for a store, and whose length differs from a taken one's, so a condition that depends on a secret shows in the trace, as a branch's does. `admin/prove` writes each routine's bytes from rind's release build by its symbol without rind's version, as it does the compares', or, for a routine that reads a table outside its own `.size`, the range `first..last` from the table's label through the routine's end, as `K256..sha256_block_data_order_hw` does; the proof then reads the table's words from that code.

Route: prove each against the HOL Light or Lean specs the x86_64 and aarch64 quests write (FIPS 180-4, RFC 8439, FIPS 197 and SP 800-38D, FIPS 202, the Montgomery spec), and compose with the Rust proofs as on the other targets.
- Upstream: offering this work to awslabs/s2n-bignum is optional, and there is no standing approval: stop and ask the maintainer before posting there or anywhere outside [the orgs AGENTS.md lists](/AGENTS.md#development) (decided with the maintainer on 2026-11-07 on [kixel-ai/rind#448](https://github.com/kixel-ai/rind/pull/448)).
- SHA-1 needs a FIPS 180-4 SHA-1 spec in HOL Light, which neither s2n-bignum nor the fork has; the fork's `aarch32/proofs/sha1.ml` defines its instructions.
- Lessons from SHA-512's NEON routine: name each Q register the routine reads before writing it with `GHOST_INTRO_TAC`, since a write to one D half of an unnamed Q register loses the other half; split each 128-bit bitwise operation on a `word_join` into its lanes (`SHA512_JOIN_BITWISE`), since an unsplit one makes later steps' terms grow until each takes seconds; state the message as one memory region and a pure relation to the spec's words (`sha512_neon_input`), since the stepper drops a quantified memory fact; and pass `AARCH32_ADD_RETURN_STACK_TAC` a `core_precondition_tac` that rewrites a register the prologue computes, such as `add r2, r1, r2, lsl #7`, to the core theorem's form.
- Lessons from SHA-256: keep each Q register a spec term after every step (`sha256_armv4.ml`'s `SHA256_HW_NORM_TAC`), so the 116-step loop body simulates in seconds; state each instruction lemma on lanes and prove the register's equality lane by lane (`SHA256_QUAD_EQ`), since bit-blasting a whole 128-bit register of nested sums hangs; and instantiate a rewrite whose left side is `EL t w` at the message `w`, since its free list variable otherwise matches K256's `EL t sha256_constants` too.
