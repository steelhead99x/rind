# [M] A proof's ✓ covers the macOS bytes too, or says it doesn't

## Goal

Every `benchmarks/verified.toml` row whose proof `admin/prove bytes` checks only against the Linux build either is checked against the Apple build too and passes, or carries `os = "linux"`, so no ✓ in README or BENCHMARKS.md covers macOS bytes that nothing checks.

## Plan

Found by [kixel-ai/rind#778](https://github.com/kixel-ai/rind/pull/778)'s iteration on 2026-11-16: aws-lc's Apple `.s` aligns its helpers to 32 bytes but not the function's entry, so with the entry 16 bytes off every helper call target differs from the Linux build's (P-256's first call targets entry+0x7b0, not +0x7a0). `admin/prove` builds and checks Linux targets only. #778 gave its P-256 rows `os = "linux"`. Rows already on main have the same gap: on x86_64, SHA-512, Ed25519 signing, and AES-GCM with AVX and MOVBE; on aarch64, SHA-256 and SHA-512, whose ✓ shows on the macOS bench host.

- First, make `admin/prove bytes` build each proven routine for the Apple target of its architecture (`x86_64-apple-darwin`, `aarch64-apple-darwin`) and compare it as it does the Linux build, listing which rows match.
- Static prediction, 2026-11-18, from comparing each `.linux.s` with its `.apple.s` after normalizing syntax (symbol prefixes, ELF-only directives, `.inst` as `.long`, x86 ELF `.align` in bytes): of the 105 pairs, 22 are the same text, 58 differ only in the Linux entry's `.p2align`, 16 also in alignment inside the routine, and 9 in instructions (aarch64 `adrp sym+N` as `adrp sym`, and one trailing string). Dropping the entry alignment changes no byte by itself, but each `.p2align` inside a routine pads relative to its entry, which on Apple is only as aligned as the toolchain puts functions (16 bytes on x86_64; check on aarch64). For the rows above: aarch64 SHA-256's `sha256_block_data_order_hw` has no inner alignment, so should match; aarch64 SHA-512's `sha512_block_data_order_hw` has one `.p2align 4`, so matches if Apple aligns its entry to 16; x86_64 SHA-512 and Ed25519 signing with AVX but not AVX2 (`sha512_block_data_order_avx`, inner `.p2align 4` only) should match; with AVX2 (`sha512_block_data_order_avx2`) the Apple file has an extra inner `.p2align 6`, so should differ; AES-GCM with AVX and MOVBE runs HACL's `gcm*_opt`, the same text on both. The P-256 routines, which #778 found differ, show as inner-alignment differences, which supports the method. Confirm each with the Apple build below; only that build counts.
- Aligning an Apple entry from inside `naked_asm!` does not work: rustc emits the symbol before the asm text, and in Mach-O's single `__text` section a `.p2align` there pads with no-ops after the entry, where in an ELF section of its own it pads nothing. Decided (owner, 2026-11-17): no search for a function alignment attribute at rind's minimum Rust.
- A row that differs only by alignment takes `os = "linux"` (owner, 2026-11-17), where that is the only difference; benchmarking an aligned Apple entry on the macOS host is not planned.
- A local check reported on this PR (comment of 2026-11-19, on an M1 Pro, macOS 14; not verified from the Linux host that wrote this plan): aarch64 `sha256_block_data_order_hw` matches the Linux bytes except the 2 `adrp`/`add` relocation words, and `sha512_block_data_order_hw` differs because the Apple entry sits 8 bytes off a 16-byte boundary (2024 B against 2016 B, 491 of 504 words shift), so that row needs `os = "linux"`. That is the case the static prediction above made conditional on a 16-aligned entry. x86_64 Apple rows are not covered.
- ✅ m4, in the verified epic: it is about what the proofs claim, not a CI or main failure (maintainer, 2026-11-16; rejected: m0; skipping it).
