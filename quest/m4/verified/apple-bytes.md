# [M] A proof's ✓ covers the macOS bytes too, or says it doesn't

## Goal

Every `benchmarks/verified.toml` row whose proof `admin/prove bytes` checks only against the Linux build either is checked against the Apple build too and passes, or carries `os = "linux"`, so no ✓ in README or BENCHMARKS.md covers macOS bytes that nothing checks.

## Plan

Found by [kixel-ai/rind#778](https://github.com/kixel-ai/rind/pull/778)'s iteration on 2026-11-16: aws-lc's Apple `.s` aligns its helpers to 32 bytes but not the function's entry, so with the entry 16 bytes off every helper call target differs from the Linux build's (P-256's first call targets entry+0x7b0, not +0x7a0). `admin/prove` builds and checks Linux targets only. #778 gave its P-256 rows `os = "linux"`. Rows already on main have the same gap: on x86_64, SHA-512, Ed25519 signing, and AES-GCM with AVX and MOVBE; on aarch64, SHA-256 and SHA-512, whose ✓ shows on the macOS bench host.

- First, make `admin/prove bytes` build each proven routine for the Apple target of its architecture (`x86_64-apple-darwin`, `aarch64-apple-darwin`) and compare it as it does the Linux build, listing which rows match. Done (2026-11-19): `admin/apple-bytes check`, which `admin/prove bytes` runs last, builds rind for both Apple targets as `admin/prove` builds Linux's, reads the Mach-O objects with the Rust sysroot's `llvm-objdump` (the flake's `hol-light` shell has the Apple targets, so Linux CI runs it), and compares each routine `admin/prove-bytes list` and `hol_light_proofs` name with the Linux build's, relocation fields masked, trailing padding trimmed. A routine that differs fails the check unless every `verified.toml` row of its architecture whose proof names it says `os = "linux"`; the check also lists the differing routines no row names and the rows marked `os = "linux"` whose routines match. On the M1 Pro, 267 of 273 routines match and 6 differ (aarch64 `bn_mul_mont`, x86_64 `sha512_block_data_order_avx2` and the four AES-GCM `gcm*_opt`), all in the rows marked or in no row. It reads one layout, `admin/prove`'s 16 codegen units, so a match is not a promise for another build.
- Static prediction, 2026-11-18, from comparing each `.linux.s` with its `.apple.s` after normalizing syntax (symbol prefixes, ELF-only directives, `.inst` as `.long`, x86 ELF `.align` in bytes): of the 105 pairs, 22 are the same text, 58 differ only in the Linux entry's `.p2align`, 16 also in alignment inside the routine, and 9 in instructions (aarch64 `adrp sym+N` as `adrp sym`, and one trailing string). Dropping the entry alignment changes no byte by itself, but each `.p2align` inside a routine pads relative to its entry, which on Apple is only as aligned as the toolchain puts functions (16 bytes on x86_64; check on aarch64). For the rows above: aarch64 SHA-256's `sha256_block_data_order_hw` has no inner alignment, so should match; aarch64 SHA-512's `sha512_block_data_order_hw` has one `.p2align 4`, so matches if Apple aligns its entry to 16; x86_64 SHA-512 and Ed25519 signing with AVX but not AVX2 (`sha512_block_data_order_avx`, inner `.p2align 4` only) should match; with AVX2 (`sha512_block_data_order_avx2`) the Apple file has an extra inner `.p2align 6`, so should differ; AES-GCM with AVX and MOVBE runs HACL's `gcm*_opt`, the same text on both. The P-256 routines, which #778 found differ, show as inner-alignment differences, which supports the method. Confirm each with the Apple build below; only that build counts.
- Apple build, 2026-11-18, on an M1 Pro with macOS 14.0 and rustc 1.98.1: rind built for `aarch64-apple-darwin` and `x86_64-apple-darwin` as `admin/prove` builds it for Linux, its routines read with `llvm-objdump` and compared with the Linux build's, relocation fields masked. All 252 `asm!` blocks (112 aarch64, 140 x86_64), the s2n-bignum code behind the X25519, Ed25519 scalar multiplication, P-256, P-384, P-521, and SHA-3 rows, are byte for byte the Linux bytes. A naked routine matches only where it has no inner alignment or its entry falls where Linux's padding does, and Mach-O gives it no section of its own: the entry's alignment is its offset in the codegen unit, so it changes with the build. aarch64 `sha512_block_data_order_hw` (one inner `.align 4`) is 16-aligned and matches at 16 codegen units, sits 8 bytes off at 4 (2024 B against 2016 B, 2 NOPs added, 491 of 504 words shift), and 12 off at 1 (2020 B). aarch64 SHA-256 and `sha512_block_data_order_nohw` have no inner alignment and match in every build. On x86_64, `sha512_block_data_order_avx2` and the `gcm*_opt` routines of AES-GCM with AVX and MOVBE differ by padding in every build, which contradicts the prediction above for AES-GCM; `sha512_block_data_order_avx` matched in all four builds, its entry 16-aligned each time, and `ecp_nistz256_point_add_affine`, `ecp_nistz256_point_add_affinex`, and `bn_mul_mont_nohw` matched in the linked builds. `admin/prove bytes` still reads Linux only, so none of this is checked in CI.
- Rows given `os = "linux"` from that result: aarch64 SHA-512 and Ed25519 (the first routine's alignment), and x86_64 SHA-512 and Ed25519 with AVX2, and AES-GCM with AVX and MOVBE. The x86_64 AVX SHA-512 and Ed25519 rows (Intel without AVX2) took `os = "linux"` too (owner, 2026-11-19): `sha512_block_data_order_avx` matched in every layout tried, but only because the entry landed 16-aligned, and nothing checks the Apple build. The aarch64 SHA-256 row (no inner alignment) keeps its ✓.
- Aligning an Apple entry from inside `naked_asm!` does not work: rustc emits the symbol before the asm text, and in Mach-O's single `__text` section a `.p2align` there pads with no-ops after the entry, where in an ELF section of its own it pads nothing. Decided (owner, 2026-11-17): no search for a function alignment attribute at rind's minimum Rust.
- A row that differs only by alignment takes `os = "linux"` (owner, 2026-11-17), where that is the only difference; benchmarking an aligned Apple entry on the macOS host is not planned.
- ✅ m4, in the verified epic: it is about what the proofs claim, not a CI or main failure (maintainer, 2026-11-16; rejected: m0; skipping it).
