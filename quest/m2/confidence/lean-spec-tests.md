# [M] Every executable Lean spec is tested against vectors and against rind

## Goal

Every spec the proofs' trust base trusts as a transliteration of its standard (`proofs/README.md`'s trust base: `Rind/Spec.lean`, `HashSpec.lean`, `Sha2.lean`, `Ed25519.lean`, `Rsa.lean`, `Vale.lean`, `Keccak.lean`, the SymCrypt and s2n-bignum transliterations, and the rest) runs on the published vectors for its algorithm and on random inputs compared with rind's output. A disagreement fails `admin/prove`.

## Plan

Decided with the maintainer on 2026-11-18 (/quest-plan): ✅ vectors and random testing against rind, in m2 (rejected: vectors only; no change). The hand-written specs are the least-checked part of the trust base. Today a few fixed vectors check them (`Sha2Test.lean`, `HashSpecTest.lean`, `ChaCha20Poly1305Test.lean`). libcrux shipped spec errors behind admitted proofs ([ePrint 2026/2441](https://eprint.iacr.org/2026/2441.pdf)). Cedar compiles its Lean model and random-tests it against its Rust ([arXiv 2407.01688](https://arxiv.org/abs/2407.01688)).

- Specs that compute, such as the hashes', compile into a Lean executable, or `#eval` where that is fast enough. A spec kept `opaque` in proofs, such as Vale's S-box and `MixColumns`, runs through the body the SIMD models already evaluate.
- A spec that does not run fast enough on the test inputs gets an executable twin, proven equal to what the proofs use on the inputs they pass it, and the twin is tested. That covers `noncomputable` definitions (`Ed25519.lean`'s `edDecode`, on valid encodings; `Spec.lean`'s `nist.inv`, which uses `Classical.choose`, with `nist.add` and `nist.pow`, which also recurses once per unit of the scalar; Vale's GHASH over Mathlib's `Polynomial`), `Prop`-valued checks with existential witnesses (`Rsa.lean`'s `rsassaPkcs1v15Verify` and `rsassaPssVerify`, which need decision procedures), and definitions that build a huge intermediate (`rsavp1`'s `s ^ e` before `% n`, which needs modular exponentiation). These are examples: the PR lists every spec and how it runs. An `opaque` constant (`edPow`, `edMul`, `rfcx25519`) is no rind transliteration: under the composition rule it stands for the upstream definition, and nothing is assumed of it, so no twin can be proven equal to it. Test the specs around one by running them with an executable transliteration of the upstream definition in its place, and say in the PR that this checks the surrounding spec, not the constant. A spec that gets neither is listed in the PR with why, not silently skipped.
- Vectors: Wycheproof, CAVP, and the RFCs' own, from `thirdparty/vectors/`. Random inputs: a fixed-seed generator in the runner, compared with rind's output through a small Rust driver in `admin/` (its path added to `prove.yml`'s `pull_request` paths), so a spec that agrees with every published case but drifts on others is caught.
- Add `thirdparty/vectors/**` to `prove.yml`'s `pull_request` paths, so a vector change runs the tests. Keep it within the `lean` job's budget. If a full sweep would slow every PR, run a fixed sample on PRs and the full sweep nightly, and say so in the PR.
- A spec bug this finds is fixed in the same PR along with every proof that rests on it, and the PR body says which ✓ marks it touched.

Status: first tranche done: the hash family (`HashSpec`, `Sha2`, `Sha3`: SHA-1, SHA-2, SHA-3, HMAC, HKDF, PBKDF2) runs on published vectors and on random inputs against rind through `admin/spec-vectors.rs`. Not yet covered: `Spec.lean` (ChaCha20, Poly1305, AEAD, ECDSA's `nist` operations), `Ed25519.lean`, `Rsa.lean`, `Vale.lean`, `Keccak.lean`, and the SymCrypt and s2n-bignum transliterations.
