# [S] rind-dimpl accepts the NIST-curve key shares aws-lc-rs accepts

## Goal

rind-dimpl's P-256 and P-384 key exchanges accept or refuse a peer's share exactly as dimpl's aws-lc-rs provider does, so `fuzz/fuzzer/dimpl.rs`'s `key_share` check passes and the weekly `fuzz` run's `Fuzz dimpl` job is green again.

## Plan

Found on 2026-11-14 by `fuzz.yml`. Both main's scheduled [run 43525080590](https://github.com/kixel-ai/rind/actions/runs/43525080590) and [run 43530778796](https://github.com/kixel-ai/rind/actions/runs/43530778796), dispatched from [kixel-ai/rind#743](https://github.com/kixel-ai/rind/pull/743), fail at `fuzz/fuzzer/dimpl.rs:231` with `Secp384r1`: rind refuses a share that aws-lc-rs accepts (`left: false`, `right: true`). The 23-byte input reproduces it every time with main's x86_64 fuzz binary:

```
09a0ff97fbffffff970100000340002b01db0d250c0c06
```

(`xxd -r -p` rebuilds it). [Run 43647578465](https://github.com/kixel-ai/rind/actions/runs/43647578465), dispatched from the same PR, failed the same check on `Secp256r1` with the 18-byte input `Av9paRCkAHn///cAAP8AAAIK` (base64), so the cause is likely shared by the NIST curves rather than P-384's. Decode which share the input builds before choosing a side. If aws-lc-rs accepts an encoding that rind's own P-384 agreement refuses as hostile, such as a compressed or otherwise non-canonical point, decide by AGENTS.md's rule (follow aws-lc-rs) and by what dimpl's DTLS peers send. If the harness built a share that only one side should see, fix the harness instead. Either way, add the input to the target's seeds so the corpus keeps it.

Progress so far:

`sh/fuzz-seed.sh` writes both inputs into `fuzz/corpus/dimpl`. `rind-dimpl/tests/provider.rs`'s `nist_hybrid_key_shares_match_aws_lc` covers the same edits. `rind-dimpl/src/kx.rs` `Exchange::complete` now accepts the NIST shares aws-lc-rs accepts: a compressed point, decompressed with `PublicKey::new`, and a hybrid point of the group's uncompressed length whose prefix parity matches `y`, rewritten to `0x04` before `agree`. X25519 is unchanged. kixel-ai/rind#792 only appends a test module at the end of `kx.rs`.

Both inputs decode, with arbitrary 1.5.0's `arbitrary_take_rest` as libfuzzer-sys 0.4 calls it, to `Input::KeyShare` with `Share::Edited`. The group byte selects `rind-dimpl`'s `kx::ALL`: `251 % 3 = 2` is `Secp384r1`, `16 % 3 = 1` is `Secp256r1`.

| Input | Edit | Share the harness builds |
| --- | --- | --- |
| `09a0ff97fbffffff970100000340002b01db0d250c0c06` | flips `[(0, 3)]`, cut `0` | aws-lc's fresh P-384 point, 97 bytes, prefix `0x04 ^ 0x03 = 0x07` |
| `Av9paRCkAHn///cAAP8AAAIK` | flips `[(247, 0), (0, 2)]`, cut `0` | aws-lc's fresh P-256 point, 65 bytes, prefix `0x04 ^ 0x02 = 0x06`. Index `247 % 65 = 52` is XORed with 0, so it does not change. |

The share bytes are not in the input. `fuzz/fuzzer/dimpl.rs` builds them by calling aws-lc-rs `start_exchange`, taking `pub_key()` (uncompressed SEC1), then applying that edit. One matching run produced P-384 `07e2c4d91648ead2df995e5e57914a879bca39ee8d38d964457a3de7700e8b0460753377e4863887d9b0c5cc7fb01589a43ddca560a7d5d9969d01a218de4166c787c0b7ecbda136b7c37b7dd4ff3705e5464f6c737c2986162ab18965fecd4447` (`0x07`, `y` odd) and P-256 `063a0cadbebc3cd7a98bba7bd44656a06cb3f035fdbebae96f82d1db844cdc18d80d4f9aac516861ce187c2af6584950d840c5af1dddd627daffd93e99adea59d8` (`0x06`, `y` even). `0x06` and `0x07` are SEC1 hybrid points: the same coordinates as uncompressed, with `y`'s parity also stored in the prefix.

Reproduced, before the fix, with `cargo +nightly fuzz build dimpl` and the x86_64 address-sanitizer binary `target/x86_64-unknown-linux-gnu/release/dimpl`. The assert at `fuzz/fuzzer/dimpl.rs:231` was `left: false, right: true` (`Secp384r1` or `Secp256r1`) exactly when the generated point's `y` parity matched the hybrid prefix. A mismatch made both sides refuse, so that run stayed green. One libFuzzer process often executes the input twice, so most replays crashed, which is why the CI input looked reliable. A single execution did not crash every time. After the fix, 24 replays of each seed stayed green.

aws-lc-rs 1.19 (`ParsedPublicKey::new` in `aws-lc-rs-1.19.0/src/agreement.rs`) parses `0x06` and `0x07` through `EC_POINT_oct2point`. aws-lc-sys 0.47's `crypto/fipsmodule/ec/oct.c` `ec_point_from_hybrid` accepts them only at the uncompressed length and only when `is_hybrid_bytes_consistent` says the prefix's low bit equals the last byte's low bit, then checks the point is on the curve. rind's `PrivateKey::agree` calls `from_x962_uncompressed`, which returns `KeyFormatError::Compressed` for every prefix other than `0x04` (`rind/src/mid/p256.rs`, `rind/src/mid/p384.rs`). `PublicKey::new` does not save this: `rind/src/high/sec1.rs` refuses a hybrid point on purpose.

The harness is right to show both providers the same bytes, so the change is in rind-dimpl, following AGENTS.md. dimpl does not filter the share first. DTLS 1.3 passes `key_share.entry.key_exchange` to `complete` (`src/dtls13/client.rs`, `src/dtls13/server.rs`), and DTLS 1.2 does the same in `CryptoContext::compute_shared_secret`. Conforming peers send the uncompressed point: RFC 8422 section 5.4.1 and RFC 8446 section 4.2.8. dimpl's own share is the provider's `pub_key()`, which both rind and aws-lc emit as `0x04`. Accepting hybrid does not change that handshake. It matches aws-lc on a hostile share.

`PrivateKey::agree` is still uncompressed-only. A hybrid point whose parity does not match, and the point at infinity (`0x00`, which aws-lc rejects in `EC_KEY_set_public_key`), still fall through to `agree` and are refused. Replay both seed files on `target/x86_64-unknown-linux-gnu/release/dimpl` after `cargo fuzz build dimpl`; a green run is not enough once, because a mismatched `y` used to pass.

Coverage on this branch. `nist_share_edges_match_aws_lc` gives every share form and length a peer can send a NIST group to both providers: each SEC1 prefix `0x00` to `0x08` and `0xff` at each NIST curve's compressed and uncompressed length and one byte either side, the point at infinity, empty and 4096-byte shares, and in the uncompressed, compressed, and both hybrid forms `x` or `y` all ones, `x` equal to the field prime, `x + p` for the smallest valid `x` (which only a reduction mod `p` would accept), a flipped `x` bit, the other `y`, an off-curve `y`, and one byte short or long. `mutated_key_shares_match_aws_lc` feeds every truncation, and every byte with its low or high bit flipped, of a valid X25519 share and of a NIST share in each form, and names the share if rind-dimpl panics. Both fail if the parity check or the compressed arm is removed. `rind-dimpl/tests/ctgrind.rs`'s `key_exchange_point_forms` agrees from a compressed and a hybrid point under memcheck. cargo-mutants 27.1.0 on `rind-dimpl/src/kx.rs` catches every viable mutant; the line-55 exclusion still names only the `Debug` impl's body, whose output no test can observe.

Two rules pull apart here. AGENTS.md has an adapter offer exactly its upstream provider's behavior and calls a divergence a bug, and says to follow aws-lc-rs when in doubt. RFC 8422 section 5.1.2 says DTLS 1.2 implementations "MUST NOT support other formats" than uncompressed for these curves, and RFC 8446 section 4.2.8.2 defines only `legacy_form = 4`, so this is not a case of doubt. rind's own choice so far also differs: `rind/src/high/sec1.rs` refuses hybrid points "as BoringSSL does", and `rind-aws-lc-rs/README.md` and `MIGRATING.md` list that refusal as a known difference from aws-lc-rs. dimpl's two built-in providers disagree too: its RustCrypto provider's `from_sec1_bytes` takes compressed points, and `sec1-0.8.1/src/point.rs` `Tag::from_u8` (lines 527-535) has no hybrid tag, so it refuses `0x06` and `0x07`.

A third difference remains. aws-lc-rs's `ParsedPublicKey::new` (`aws-lc-rs-1.19.0/src/agreement.rs`, lines 747-790) tries a DER `SubjectPublicKeyInfo` before the raw point, so dimpl's aws-lc-rs provider takes a share wrapped in one, for X25519 as well as the NIST groups. rind-dimpl refuses it. `spki_key_shares_are_refused` pins that. The fuzzer's `Share::Edited` cannot lengthen a share into one, so it does not fail the job today. `rind-dimpl/README.md` lists that refusal.

## Waiting

- Maintainer: how strictly rind-dimpl parses a peer's key share. Options: (a) exact aws-lc-rs parity, adding the `SubjectPublicKeyInfo` form. `PublicKey::from_spki`, which rind-aws-lc-rs uses, is not enough: on P-256 it takes WebCrypto's `id-ecDH` algorithm, which aws-lc-rs refuses, and refuses a hybrid point inside `id-ecPublicKey`, which aws-lc-rs takes, so rind-dimpl would have to refuse `id-ecDH` and apply its hybrid rule to the inner point; (b) as this branch does, compressed and parity-matched hybrid points but no `SubjectPublicKeyInfo`; (c) compressed points only, as rind-aws-lc-rs and `PublicKey::new` do, listing the hybrid and `SubjectPublicKeyInfo` refusals in `rind-dimpl/README.md` and having `fuzz/fuzzer/dimpl.rs` skip the comparison for those prefixes; (d) uncompressed only, as RFC 8422 section 5.1.2 requires, with the same README entry and fuzzer exception for every other form. Recommendation: (c), which keeps one hybrid policy across rind and matches both of dimpl's own providers on compressed points. Done when the answer is recorded in this Plan and the branch implements it.
