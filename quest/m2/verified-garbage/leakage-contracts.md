# [M] rind imports pyca/verified-garbage's leakage contracts, and retires the harnesses they cover

## Goal

For each VG routine rind runs, its leakage theorem is imported as an axiom about the routine's artifact on VG's model, stated with the vendored `VerifiedGarbage/TCB/Artifact.lean`'s own trace definitions and citing VG's theorem at the pinned revision, with `admin/vg-bytes` checking that rind's build emits that artifact's bytes. Today it compares instruction bytes and relocations by the symbol's last path component only; extend it to bind each relocation's full target and the contents of the statics it reaches before any harness retires: the routine's address and branch trace depends only on what its contract declares public. It says nothing about rind's Rust wrapper, so [the composition rule](/quest/m4/verified/README.md#composition-rule)'s one functional axiom per wrapper is unchanged; `Axioms.lean` pins the new axioms too. The dedicated constant-time harness of each such routine is removed: `ct_sde_…` for VG's ML-KEM-768 and P-256 on x86_64, `ct_qemu_…` for its aarch64 SVE2 ChaCha20-Poly1305, and any `ct_binsec_…` region over only VG code. TESTING.md's constant-time column cites the theorem instead.

## Plan

Follow-up from the 2026-11-18 /quest-plan on independence and Lean, which settled with the maintainer: ✅ once a routine's leakage contract is proven in Lean, its dedicated trace harness is retired, and ctgrind keeps running every test (rejected: keep every harness). VG already proves these contracts (`VerifiedGarbage/TCB/Artifact.lean`). Today rind restates only what each wrapper returns (`Rind/VgOutcome.lean`, `Rind/<Arch>/VgMlKem.lean`), so the harnesses still carry the claim. Kept as a follow-up by the maintainer on 2026-11-18, on [kixel-ai/rind#893](https://github.com/kixel-ai/rind/pull/893): ✅ keep (rejected: drop).

- A contract's declared leakage, such as a rejection-sampling count, must be public in rind's call too. Check each against the Rust that calls the routine, and keep the harness for any routine whose declared leakage rind's caller treats as secret.
- The theorems need the cosimulation that the ✓ needs, which `admin/prove vg` already runs for these instructions. The stack-slot model gap recorded in [the epic](/quest/m2/verified-garbage/README.md) holds back only the routines it holds back there.
- Where rind's Rust feeds a VG routine, ctgrind and BINSEC still check that Rust. An SDE or QEMU harness also traces the wrapper on a path valgrind cannot run and BINSEC does not decode (AVX-512, SVE2), so before retiring one, give that wrapper a retained trace check, such as a BINSEC region over it with the VG routine stubbed by its contract, and say which in the PR. Retire a BINSEC region only when it covers VG code alone.

## Waiting

- Maintainer: how the axiom names the routine's code. Decided (a): vendor each routine's `Impl/` closure, and state `Verified`'s constant-time conjunct (`ConstantTime`) of VG's own `Prog` (`Cosim/Progs.lean`). Done for aarch64 SVE2 ChaCha20-Poly1305 (`Rind.Aarch64.VgChaCha20Poly1305Ct`, 2,859 added Lean lines); `admin/vg-bytes --progs` checks that VG's printer's text of that `Prog` and of every function it calls is VG's assembly, line for line, and the machine code is checked against that text. That `Prog` is the printed text only if VG's printer is injective on it, which it is not in general, so the link rests on VG's printer, which is vendored and in the trusted base. Left: ML-KEM-768 on x86_64 (about 7,300 added lines) and P-256 IFMA ECDH on x86_64 (about 19,000), each by the same steps.
- Maintainer: the retained trace check for each wrapper whose SDE or QEMU harness retires. No `ct_binsec_...` region decodes AVX-512 or SVE2, so `ct_sde_mlkem768` (rind's `keygen_internal`, `encaps_internal`, `decaps`, which are rind's Rust around VG's routines), `ct_sde_p256_ifma_ecdh`, and `ct_qemu_chacha20poly1305` would leave their wrappers without a trace check. Either BINSEC gains those decoders, or a region stubs the VG routine by its contract on the portable parts, or the maintainer accepts ctgrind alone for the part of each wrapper valgrind runs. Until then `ct_qemu_chacha20poly1305` stays, though its routine's leakage is now an axiom. Clear it by choosing one.

Checked for the Plan's first bullet, at VG `0aa40d6c`: each declared leak is public in rind's caller. ML-KEM-768's `leakRho` is `ρ`, which is in the encapsulation key; P-256 ECDH's `leak` is the peer's public key bytes; ChaCha20-Poly1305 open's `openLeak` is whether it returns 1, which rind returns. So no harness stays for that reason.
