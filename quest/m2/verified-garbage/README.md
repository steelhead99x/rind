# rind runs pyca/verified-garbage's proven code wherever it is fastest

## Goal

On every tier where [pyca/verified-garbage](https://github.com/pyca/verified-garbage) (VG) measures at least as fast as what rind runs, at every size the speed bar sets, rind runs VG's routine under its own glue and behavior, and that cell earns the ✓ once the instructions its proof rests on are cosimulated.

## Plan

Decided with the maintainer on 2026-11-12, in `/quest-plan`:

- VG is an Apache-2.0-or-BSD-3-Clause library written by LLMs. Its assembly is written in Lean over Lean models of each ISA and proven correct and constant time (memory and branch traces) in Lean v4.35.0, the toolchain `proofs/` uses, then printed as Rust naked functions in its `crates/verified-garbage-asm-<target>/`. It proves its own code, not the aws-lc and BoringSSL code rind runs, so rind gets a VG proof only by running VG's code.
- ✅ Measure, then switch per primitive and tier where VG is fastest (rejected: measure only and decide later, or take only ideas and no VG code). This is `AGENTS.md`'s fastest-permissive-source rule. Each switch also replaces a HOL Light proof of the code it retires.
- The ✓: ✅ switch the code once it measures fastest; the ✓ waits until [the routine's instructions are cosimulated](/proofs/README.md#verified-garbages-models) (rejected: a ✓ at once with VG's models listed as trusted, which lowers the bar rind holds its own s2n-bignum additions to; or no switch before cosimulation, since speed and proof are separate claims). VG's ISA models are LLM-written and checked only against vendor manuals and golden values. Its encoder is checked only by golden tests, and no CI step decodes the bytes it emits.
- ✅ VG becomes a permanent library in rind-bench, the benchmark report, and the weekly bench's tiers (rejected: a one-off harness, which goes stale at VG's pace). This extends the report's library list settled on 2026-11-03.
- ✅ The nine unstarted m4 proof quests whose code VG may replace wait on the measurement below (rejected: keep them ready). These are ChaCha20-Poly1305 (x86_64 cipher and AEAD, aarch64), P-521, RSA (signing, x86_64 Montgomery, x86_64 IFMA), and ML-KEM's AVX-512 sampler and portable arithmetic. In-flight PRs continue.
- ✅ m2 (rejected: m4 as a proof route, which delays the speed wins behind m3). m2 follows the release MoQ switches to, so hot paths don't change under it.

Settled by the agent, from `AGENTS.md`:

- Behavior: a switch takes VG's lowest routine that leaves rind's API and behavior intact, and keeps rind's glue. Rind follows aws-lc-rs where VG differs: rind signs ECDSA with hedged nonces where VG is deterministic (RFC 6979), refuses small-order Ed25519 keys where VG doesn't, and wipes as AGENTS.md's wipe rule says, not VG's secret-residue rule. ✅ That rule's exception keeps the stack-scratch wipe (and, on x86_64, the register wipe) a VG routine's proof covers (rejected: waiting for VG builds without the wipe), decided by the maintainer on 2026-11-17 in [kixel-ai/rind#813](https://github.com/kixel-ai/rind/pull/813#issuecomment-6942591536).
- Code: the first switch adds `admin/import-vg`, which vendors VG's generated code byte for byte from a pinned VG commit, as `admin/import-aws-lc` does for aws-lc. It also updates `AGENTS.md`'s list of verified sources and [the m4 verified epic](/quest/m4/verified/README.md)'s routes.
- Cosimulation: `admin/prove vg` checks each instruction of VG's code at `admin/import-vg`'s pin, from whose `REV` `admin/import-vg-models` vendors VG's ISA models into `proofs/verified-garbage/`, against the CPU, or under Intel SDE or qemu-aarch64 where the CPU lacks a feature it needs. Branches without a condition (`jmp`, `b`), static addresses, and a lone `ret` are left to the bytes check and to the call cases that run `ret`, as [the proofs README](/proofs/README.md#verified-garbages-models) says. It also checks that each `vg_*` routine rind vendors is VG's text at that pin, and `admin/import-vg-models --check` fails until the models are VG's at that same pin. A ✓ quest whose theorem states a VG `Spec/` module adds it to that script's `ROOTS`.
- Model gaps: reviewers found two gaps in VG's ISA models that the cosimulation of single instructions cannot catch, both reported upstream. The maintainer ruled on them on 2026-11-17 ([kixel-ai/rind#815](https://github.com/kixel-ai/rind/pull/815#issuecomment-6943056592)):
  - Stack slots: a freed frame's bytes keep their values in the model, so a proof can read back a value a signal handler may have overwritten on hardware ([pyca/verified-garbage#5321](https://github.com/pyca/verified-garbage/issues/5321)). ✅ Report it, and each ✓ quest waits under `## Waiting` for VG's fix and a re-pin (rejected: a rind-side check that each stack load reads only bytes its own frame stored; accepting the model as is). VG fixed both models ([pyca/verified-garbage#5378](https://github.com/pyca/verified-garbage/pull/5378) and [#5391](https://github.com/pyca/verified-garbage/pull/5391)) by `0aa40d6c`.
  - `NoResidue` counts two undefined flags as equal, so it accepts secret-dependent SF and ZF after `imul` ([pyca/verified-garbage#5322](https://github.com/pyca/verified-garbage/issues/5322)). ✅ Report it; it holds no ✓, since rind imports no `NoResidue` theorem and wipes by its own `wipe` rule (rejected: not reporting it).
  - A gap found later goes to the maintainer, who rules on how ✓ quests treat it and approves or drops reporting it upstream.
- Proofs: each ✓ imports a VG routine's theorem as one axiom about rind's opaque wrapper, under [the m3 epic's composition rule](/quest/m3/verified/README.md). VG's proofs as a Lake dependency were ruled out: one routine's import closure is 155 to 650 modules (50k to 176k lines, against `proofs/Rind`'s 38k), and needs VG's 18 GB build cache.

Measured on 2026-11-13 at VG `d004ffae` ([kixel-ai/rind#741](https://github.com/kixel-ai/rind/pull/741)), VG's time over rind's: every bench tier in [run 43531095881](https://github.com/kixel-ai/rind/actions/runs/43531095881) (x86_64 native on a Zen 4 EPYC 9V74 with AVX-512, the forced x86_64 tiers on Zen 4 and Xeon 6975P runners, aarch64 and armv7 on Neoverse N2), the idle Haswell VPSes `ovh-iad` and `ovh-sea` at the report's sizes, and `desktop` (Arrow Lake) at every size but under load, about 10 of 24 CPUs busy, so its numbers only suggest. On 2026-11-17, at VG `e7b0fe8a`, rind-bench's rind and VG rows ran at every size on `kixtop` (Apple M4, 1.6 of 10 CPUs busy with other work, above the report's limit of 1.0 there, so its numbers are noisy) and `nixos` (Zen 3 with AVX2 and ADX, 8.1 of 32 CPUs busy, then the curve, RSA verification, and SHA-3 rows again with 2.11 busy, under the report's limit of 3.2 there, a tenth of the CPUs), as [kixel-ai/rind#852](https://github.com/kixel-ai/rind/pull/852) records. They agree with the cells above; what they add:

- Zen 3 with AVX2 won X25519 ECDH (0.97, 0.98), Ed25519 key generation and verification (0.98, 0.78), P-256 ECDH, signing, and verification (0.80 to 0.99), and P-384 every operation but ECDH with a stored key (1.02); X25519 key generation (1.04), Ed25519 signing (1.01), and P-256 key generation (1.01 to 1.07) lost.
- The M4 won P-256 every operation but key agreement's key generation (1.03), P-384 signing, key generation, and verification (0.79 to 0.98), PBKDF2 (0.79 to 0.84), SHA-3 (0.77 to 0.95; rind holds DIT around hashing where VG does not, about 37 ns a call there, so allowing for it 0.92 to 0.98), and ChaCha20 from 1200 B (0.57 to 0.75). It lost P-384 ECDH (1.04, 1.11) and level-or-lost X25519 and Ed25519 (0.98 to 1.27).
- Only on the M4, so not a cell, since the N2 lost them on the same tier: ML-DSA key generation (0.91 to 0.95, the N2 1.00 to 1.03) and AES header protection (0.89, the N2 1.20 to 1.23).

The epic's quests hold each cell VG won. VG lost these, at its worst size:

- AES-GCM, every tier: 1.24 to 2.65 at 32 B (VG is level or ahead only at 16 KB); armv7, where VG has no NEON AES, 24 to 53.
- AES-CTR and AES-CBC: 1.7 to 7.4 at 32 B, and 48 to 139 on armv7. VG's API takes the IV only with the key and its types are not `Clone`, so its rows expand the key per message, which rind's don't: recheck if VG adds a way to reuse a key.
- ChaCha20-Poly1305 on x86_64: AVX-512 1.14 (512 B), no AVX2 1.68, the Haswell VPSes 1.10; level without AES-NI or SSSE3 (up to 1.01). ChaCha20 and AES header protection: 1.12 to 1.37. AES-128 on the Haswell VPSes first measured 0.92 and 0.96, but rechecked on 2026-11-17 with VG's `vg_aes_ecb_encrypt_aesni` under rind's glue (rind's round keys are VG's schedule, so it takes them as they are), the routine took 1.15 and 1.17 times rind's time on `ovh-sea` and `ovh-iad` (7.7 and 8.0 ns against 8.8 and 9.4 ns, four interleaved rounds each), 1.22 on Arrow Lake, and 1.7 on Zen 3: the routine loops over a round count and wipes its registers, while rind's AES-128 block is straight-line, and VG's public API rows measured level (1.0 to 1.07) there too. No AVX2 CPU without VAES is available besides those two VPSes, since `nixos2` was removed.
- SHA-3 and SHAKE ([kixel-ai/rind#851](https://github.com/kixel-ai/rind/pull/851), [run 44175298388](https://github.com/kixel-ai/rind/actions/runs/44175298388)): VG's 0.46 to 0.54 on Neoverse N2 came from rind running Keccak-f on the SHA3 instructions, which run at half the speed of scalar code there; rind now takes them only on Apple targets, as VG and mlkem-native do, and VG measured 1.05 to 1.08 at 32 and 64 B. x86_64 runs the same code on every CPU: VG 0.91 to 0.98 on the Xeon 6975P runners, but 1.01 to 1.05 from 1200 B on Zen 4 and 1.04 at 1350 B and 1.03 at 16 KB on `nixos`'s Zen 3, so rind keeps its proven code. On the Apple M4, where VG takes FEAT_SHA3's Keccak, VG won at 0.92 to 0.98 once rind's DIT toggle is allowed for (above).
- SHA-256, SHA-512, SHA-1, and their HMAC and HKDF: SHA-256 1.11 to 1.23 at 32 B with SHA-NI or AArch64's SHA-2 (on the M4 VG's API took 0.45 of rind's time at 32 B, but against rind with DIT held it lost, 1.14; SHA-1 and SHA-512/256 lose the same way once DIT's cost is allowed for), 3 to 6 on armv7; SHA-512 1.05 to 1.18; HMAC 1.12 to 2.3 at 32 B; HKDF expand 1.6 to 2.1 (VG has no HKDF, so its rows run RFC 5869 over VG's HMAC).
- X25519 and Ed25519 without AVX-512: 1.11 to 1.56 on the 2026-11-13 x86_64 tiers and VPSes (Zen 3's mixed results are above), 1.01 to 1.27 on aarch64, 3 to 33 on armv7 (VG's generic 32-bit code).
- P-521, every tier but the portable one: 1.03 to 1.69 (ECDH up to 1.32, signing 1.03 to 1.17, verification 1.09 to 1.69).
- ML-DSA key generation 1.02 to 2.43; verification up to 1.09 on x86_64 (ML-DSA-87 0.96 with AVX-512, but ML-DSA-44 1.03), 1.01 to 2.66 on aarch64; signing with AVX2 1.04 to 1.10, aarch64 0.99 to 1.05; armv7 1.8 to 2.1.
- ML-KEM-768 decapsulation without AVX-512: 1.17 to 2.48.
- RSA, but for the cells in its quest: private operation with ADX but without IFMA 1.02 to 1.65 (VG won 3072, 6144, and 8192 bits on the no-IFMA tier, but not every size), the Haswell VPSes about 2.0 to 2.2 (no ADX), aarch64 signing 1.03 to 1.31, armv7 1.2 to 3.8, and key generation below 4096 bits 1.26 to 1.74.
- Not cells: the portable tier, where VG won nearly everything (0.29 to 1.00), times VG's x86_64 assembly against rind's portable Rust, which runs only where rind has no assembly; and the `rsa*-load` rows time VG's import from parsed components against rind's DER parse.
