# [S] Benchmark report refresh, before rind 0.4 is released

## Goal

`BENCHMARKS.md`, and with it the README's heatmap, is regenerated on every host in `admin/bench-report`'s `HOSTS` shortly before rind 0.4 is released, and every new gap is triaged as the Plan sets out.

## Plan

Decided with the maintainer on 2026-11-03: rerun the report regularly. On 2026-11-09: ✅ once before each minor release (rejected: at the end of each milestone; leaving it there). The 0.4 refresh ran in [kixel-ai/rind#619](https://github.com/kixel-ai/rind/pull/619). Decided 2026-11-21 (orchestrator, for the maintainer, in [kixel-ai/rind#949](https://github.com/kixel-ai/rind/pull/949), which added `fedora`): ✅ a second refresh before 0.4 (rejected: rerun every host in that PR; no refresh before 0.4). 0.4 now waits for more than it did when the first refresh ran, and several VG switches have landed since, so that run no longer shows what 0.4 ships.

- It is ready now: every breaking change [rind 0.4](/quest/m2/api/release-0.4.md) waits for is on `main`, so it measures what ships. The release quest requires this one. The PR that finishes it deletes this file with `quest rm`, which clears that link. The next minor release's quest creates the next run at this path, carrying this Plan forward from git history.
- Run `admin/bench-report collect` for every host, then `render --from`. Review the diff for regressions, and triage gaps above 10% into speed quests or recorded reasons in `benchmarks/gaps.toml`, which `render` requires. The weekly bench's `gate` job owns regressions on the CPU tiers and this run owns the report: the hosts, the libraries the weekly bench leaves out, and the README's claims.
- Drop each `gaps.toml` entry that says the next refresh measures or rechecks it, once this run's data shows it closed: today those for [kixel-ai/rind#847](https://github.com/kixel-ai/rind/pull/847) (P-384 signing), [#913](https://github.com/kixel-ai/rind/pull/913) (armv7 NEON AES), [#944](https://github.com/kixel-ai/rind/pull/944) (portable SHA-2), and the noise and recheck entries on `nixos`, `ovh-sea`, and `kixtop`.
- Every host but `kixtop` must give a quiet, successful result: rerun a host whose run is marked noisy, skipped as busy, failed, or unreachable until it does, since `render --from` keeps a missing host's earlier data and noise opens false gaps (`fedora`'s one noisy run in [kixel-ai/rind#949](https://github.com/kixel-ai/rind/pull/949) timed rind's Ed25519 signing at 4.8× its quiet time). `kixtop` is often offline; if it stays offline, say so in the PR and keep its last data.
- Settled with the maintainer when the report was planned (2026-11-03), so don't reopen them: each host on its native path; the libraries rind, aws-lc-rs, ring, RustCrypto with dalek, graviola, libcrux, and OpenSSL, to which pyca/verified-garbage was added (maintainer, 2026-11-17), so this run triages its cells too, as [the VG epic](/quest/m2/verified-garbage/README.md) sets out; a ✓ only where a published proof covers the whole computation that library runs on that host, padding included.
- The bar, settled for the m2 speed epic (maintainer, 2026-11-01): the fastest permissively licensed source usable from Rust, on every x86_64, aarch64, and armv7 tier the weekly bench forces, at symmetric sizes 32 B, 1200 B, 1350 B, and 16 KB (plus 64 B and 8 KB for hashes, and 128 B, 256 B, and 512 B for AEADs). Copyleft sources don't count. AGENTS.md's source rule says which source runs; the 1.10× threshold for a `gaps.toml` decision is separate.
- Triage (maintainer, 2026-11-09): the PR records each gap that needs a quest as a follow-up in its body, and the `gaps.toml` entry names that quest once it exists.
- Read each host's every-logical-CPU handshake rows against its last run, and open a quest for a host where rind-rustls's scaling falls or trails aws-lc-rs's.
- Recheck the README's opening against the new results: its claims, such as which operations trail aws-lc-rs and ring, must still hold.
