# [XS] The merge queue runs rind's tests natively on aarch64

## Goal

Every merge group builds and runs rind's tests natively on aarch64, on the maintainer's Mac mini as a second self-hosted runner beside the x86_64 one, and the group fails if they fail. It covers macOS on Apple silicon and aarch64 Linux in a VM on the same machine. armv7 stays out (Apple silicon has no AArch32); the `check:cross` work in [kixel-ai/rind#594](https://github.com/kixel-ai/rind/pull/594)'s quest covers its compilation.

## Plan

Planned with the maintainer on 2026-11-10, after [kixel-ai/rind#583](https://github.com/kixel-ai/rind/pull/583) and [kixel-ai/rind#564](https://github.com/kixel-ai/rind/pull/564) passed the x86_64-only queue but together broke aarch64 tests: ✅ the maintainer bought a Mac mini for rind; ✅ its roles are this queue runner, a benchmark host ([its quest](/quest/m2/bench/mac-mini.md)), Apple-silicon nightlies ([its quest](/quest/m2/confidence/apple-nightlies.md)), and an agent workstation; ✅ this quest in m0, the others in m2 (rejected: all m2; all m0).

- Decided 2026-11-25 (maintainer, /quest-run): the Mac mini is set up and reachable as `ssh mini` (Apple M5 Pro, macOS 27.2.1, admin account `kixelated`, Nix installed; `sudo` asks for a password, so prefer a setup that needs none, such as a per-user runner LaunchAgent and an unprivileged VM).
- Built in [kixel-ai/rind#1022](https://github.com/kixel-ai/rind/pull/1022): `admin/mac-mini-runners` runs both runners in tart VMs on the Mac mini (macOS 27.2 and Ubuntu 24.04), each as an unprivileged guest user behind a guest firewall that admits only the internet, so a group's code reaches neither the maintainer's account nor the host, LAN, or tailnet. Both join the `rind-queue` runner group, which already admits only `queue-build.yml` at `refs/heads/main`, with labels of their own. `queue-build.yml`'s `Build aarch64 macOS` and `Build aarch64 Linux` jobs run only the host `rs` module, the one whose result depends on the host; the x86_64 build already lints and compiles every target.
- Measured on 2026-11-25, both VMs at once with 8 vCPUs each: a group's aarch64 job takes 3 to 5 minutes (macOS 213 to 288 s, Linux 197 to 311 s, a cold store the slower end), while the x86_64 build took a median of about 18 minutes over its last 30 groups. So today it adds no time to landing; once [the thin merge queue](/quest/m0/ci-speed/thin-merge-queue.md) cuts the x86_64 build to a couple of minutes, these jobs set the group's time, about 2 to 3 minutes more, until [the warm build cache](/quest/m0/queue-warm-target.md) reaches them too.
- `quest gate` in each job gates within its VM; the host's agents and the VMs share the CPU through macOS's scheduler, not the gate.
