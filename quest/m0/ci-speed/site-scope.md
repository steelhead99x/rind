# [S] Scope check:site to site inputs and drop its duplicate PR run

## Goal

`check:site` in `sh/dispatch.sh` runs only when a diff touches `site/`, `sh/site.sh`, or one of the repository files `site/src/lib/repo.ts`'s `sources` reads (plus file deletions/renames that could break repo links), pull requests no longer run the site build twice across both `site.yml` and `pr-check.yml`, and release-plz's release PRs still get a site check once the thin merge queue stops running it.

## Plan

Measured across recent PR and merge-queue runs: `check:site` runs `bun install --frozen-lockfile`, `bun test`, `bun run build`, and headless Chrome (`sh/site.sh`) for 43–151s on **every** diff (`module site ''` in `sh/dispatch.sh`), including pure quest or Rust PRs, and `site.yml` runs the exact same `sh/site.sh` a second time in parallel on every pull request.

- ✅ Scope `check:site` to site/doc/README paths only and eliminate the duplicate run between `pr-check.yml` and `site.yml` (maintainer, 2026-11-21).
- `site/src/lib/repo.ts` already declares the exact repository files `site/` reads (`README.md`, `BENCHMARKS.md`, `MIGRATING.md`, `benchmarks/report.json`, `admin/wordmark.svg`, `admin/wordmark-light.svg`, and each routed adapter's `README.md` and `Cargo.toml`). Scope `module site` in `sh/dispatch.sh` to those paths plus `site/`, `sh/site.sh`, `sh/dispatch.sh` (which holds `check:site`'s command and this scope), `flake.nix` (which defines the site shell's Bun and Chromium), `flake.lock`, and `.github/workflows/pr-check.yml` with the composite actions it runs (`.github/actions/just/`, `.github/actions/nix/`), which set up the environment the site builds in, and run it on any diff that deletes or renames a file (`git diff --diff-filter=DR`), since the site also links repository files outside `sources`, such as `ALGORITHMS.md`, `CONTRIBUTING.md`, `LICENSE`, and quest files, whose loss its link check catches. That check (`site/scripts/check.ts`) also resolves each link's anchor or line range, such as `proofs/README.md#trust-base`, so an edit to such a file can break a link too: the scope also covers every repository file the site links on `main` with a fragment, listed in a checked-in manifest such as `site/anchored.txt`. The build can quote an adapter's README from crates.io rather than the checkout (`choose` in `site/src/lib/readme.ts`), so its links change when a release publishes, with no change to the checkout: `check.ts` therefore fails when the build, or the checkout's own copy of a routed README, which its next release publishes, links with a fragment a file the manifest lacks, and never on an extra entry, which costs only a site run on that file's edits. A release PR then adds its README's new entries before it publishes, and main's build stays green after. Edits to a linked file no fragment names keep its links, so they need no site run.
- Remove the duplicate run by dropping `site.yml`, so path-scoped `pr-check.yml` covers it and the path list lives in one place (`sh/dispatch.sh`). [kixel-ai/rind#958](https://github.com/kixel-ai/rind/pull/958) deletes `site.yml`; if it lands first, this part is done.
- `pr-check.yml` skips release-plz's release PRs, which `site.yml` checks today and the queue's `just ci` checks after it, and a release PR bumps each routed adapter's `Cargo.toml`, which the site reads. Once `site.yml` is gone and the [thin merge queue](/quest/m0/ci-speed/thin-merge-queue.md) drops `site`, nothing would check those PRs before they land. So on a release PR, `pr-check.yml` runs with `CHECK_MODULES=site` instead of skipping the job: the scoped `site` module, and no `rs` build of the bumped crates.
