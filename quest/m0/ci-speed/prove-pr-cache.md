# [M] Pull requests re-check only the proofs whose inputs changed

## Goal

On a pull request, `prove.yml` reruns an architecture's HOL Light proofs only when an input of one of them, such as its object bytes, a proof file it loads, rind's s2n-bignum fork, or the proof environment, changed since a run that passed. It runs `admin/prove cosim` only when the fork's instruction-model files, the AArch32 model, or cosim's own driver and harness changed. The nightly run still checks everything and reads no cached result: it only writes the cache, so a stale or planted entry never hides a failure there (maintainer, 2026-11-19: ✅ an uncached nightly; rejected: a nightly that trusts the cache).

## Plan

Decided with the maintainer on 2026-11-18 (/quest-plan): ✅ cache each HOL Light result and scope cosim (rejected: run everything on every pull request). Why: in the 30 hours from 2026-11-17 12:00 UTC, pull requests spent about 327 hosted machine-hours on `prove` (143 runs). Per run, `hol-light-aarch64` averaged 50 minutes, `hol-light-x86_64` 35, `cosim` 26, `lean` 25, and `hol-light-armv7` 10. Most of those pull requests changed no proven assembly, and none changed the models cosim checks.

- `admin/prove hol-light` loads an architecture's proofs, then its `hol_light_specs` known-answer tests, into one OCaml program, so each result also depends on the bindings everything before it leaves. Key each result, proof or spec test, on everything that program loads up to and including it: each `.ml`, directly or through `needs` (which resolves `proofs/hol-light/` first, so `ecp_nistz256_point_add_affinex.ml` reaches `ecp_nistz256_point_add_affine.ml`); each object those proofs extract (the bytes, the relocations, and the read-only data they reach); the `hol_light_data` statics they assert (such as `sha256_shaext_k.bin`, SHA-256's `K` table, which can change without the routine's bytes changing); the fork's tree, which holds what the base files load (such as `common/words2.ml`); `admin/prove` itself, `prove.yml`, and the `.github/actions/nix` setup it runs; and the proof environment (`flake.lock` and the `flake.nix` shell that pins HOL Light and OCaml). A key that misses an input reports a pass for a result that was never rerun, so when in doubt, key on more. A cache hit must still run `admin/prove bytes`, which is cheap and checks that the build emits those bytes. The pull request builds rind anyway, so extract first. Since a key covers everything before it, a miss reruns its program from the start, every proof before it included, as their bindings are its input; a program whose results all hit is skipped. Finer skipping, such as resuming from a checkpoint after the hits, is this quest's PR to measure.
- Store the keys where a pull request from a fork cannot write them, such as an artifact or the Actions cache from `main`'s nightly run only. A pull request may read the cache but never populate it, so a malicious pull request cannot plant a passing result.
- Cosim's trigger covers what can change its result: everything it loads, directly or through `needs` and `loadt` (which reaches most of the fork's tree, so trigger on the tree), the model files, `admin/prove`'s `cosim` path, the cosimulation harness and its inputs, its job in `prove.yml`, and its environment (`flake.nix` and `flake.lock`, which give it the `hol-light` shell and `qemu-arm`).
- `prove.yml`'s `pull_request` paths miss build inputs that can change the proven bytes: `Cargo.lock`, `Cargo.toml`, `rind/Cargo.toml`, `rind/build.rs`, and `.cargo/**`. Add them, and `.github/actions/nix/**`, which the key covers, since the cache makes a run that changes no proof cheap.
- The Lean job stays as it is: Lake already rebuilds only the modules that changed.
- Give the per-run machine time before and after in the PR, as the epic does.
