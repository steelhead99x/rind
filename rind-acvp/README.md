# rind-acvp

Unpublished. A module wrapper for [BoringSSL's and aws-lc's `acvptool`](https://github.com/aws/aws-lc/tree/main/util/fipstools/acvp/acvptool): that tool speaks ACVP's sessions and JSON, and this binary runs the operation.

```shell
# From a checkout of aws-lc. The binary has to be on PATH.
go build -o acvptool ./util/fipstools/acvp/acvptool

admin/acvp
```

`admin/acvp` runs `cargo test -p rind-acvp`, then `acvptool -wrapper <binary> -json` on every sample set in `thirdparty/acvp` that this wrapper answers. It compares every required deterministic result field to the published answer and rejects missing, duplicate, or unexpected replies, including missing Monte Carlo results. Generated keys and signatures are checked for nonempty encoded results; `acvptool` also asks the wrapper to verify fresh ECDSA and RSA signatures. Cargo's target directory determines the binary path; `RIND_ACVP_WRAPPER` can override it. `ACVP_SKIP_TOOL=1` runs the crate tests only. Without `acvptool` on `PATH`, the script stops and prints the build line above. Arguments select individual sets, for example `admin/acvp PBKDF-1.0 hmacDRBG-1.0`.

The sample files are `internalProjection.json` and carry both inputs and answers. The script strips fields `acvptool` reads as inputs (AES-GCM's `ct` and `tag` on an encrypt test), gives each HMAC test its own length group, and concatenates a KDA hybrid secret's `t` onto `z` because `acvptool` forwards only `z`. It removes the legacy `externalMu: false` field from ML-DSA external-interface groups: only internal groups use that field, and its absence tells `acvptool` to send the external interface, even for an empty context. All ML-DSA signing and verification samples run. These adaptations are tracked in [UPSTREAM.md](../UPSTREAM.md#acvptool-expects-older-sample-formats).

The runner also sends supplemental prompts through `acvptool`: SHA-1 against Python's `hashlib` (the vendored files have no SHA-1 set), PBKDF for every advertised hash against Python's `hashlib`, HMAC_DRBG generation, reseeding, and prediction resistance against an independent SP 800-90A implementation using Python's `hmac`, KAS-ECC-SSC on P-256/P-384/P-521 against the vendored CAVP ECDH answers for every advertised scheme and role, and HKDF multiple expansion through its 255-block limit against Python's `hmac`. These cover operations missing from the vendored ACVP files.

`prompts.json` for a direct `acvptool` invocation is a JSON array of vector sets, prompts only. `cargo test -p rind-acvp` checks sample answers by calling handlers and exercises the executable's byte framing with published SHA, HMAC, PBKDF, DRBG, and ECDH vectors. The standard Monte Carlo groups also run. The vendored SHA-256 set has the alternate Monte Carlo, which `acvptool` does not drive. Each framed reply explicitly flushes stdout, so the client receives it while keeping the same wrapper process open.

`acvptool -wrapper <binary> -regcap` emits the registration. Its domains follow NIST's [symmetric](https://pages.nist.gov/ACVP/draft-celi-acvp-symmetric.html), [MAC](https://pages.nist.gov/ACVP/draft-fussell-acvp-mac.html), [PBKDF](https://pages.nist.gov/ACVP/draft-celi-acvp-pbkdf.html), [HKDF](https://pages.nist.gov/ACVP/draft-hammett-acvp-kas-kdf-hkdf.html), [ECDSA](https://pages.nist.gov/ACVP/draft-fussell-acvp-ecdsa.html), [EdDSA](https://pages.nist.gov/ACVP/draft-celi-acvp-eddsa.html), [KAS-ECC-SSC](https://pages.nist.gov/ACVP/draft-hammett-acvp-kas-ssc-ecc.html), [RSA](https://pages.nist.gov/ACVP/draft-celi-acvp-rsa.html), [ML-KEM](https://pages.nist.gov/ACVP/draft-celi-acvp-ml-kem.html), [DRBG](https://pages.nist.gov/ACVP/draft-vassilev-acvp-drbg.html), and [ML-DSA](https://pages.nist.gov/ACVP/draft-celi-acvp-ml-dsa.html) registration tables. HMAC registers revision 1.0, whose group-level lengths this client reads. HKDF requests non-hybrid secrets because the client drops `t`. ML-KEM encapDecap registers `FIPS203-tr1` with expanded keys and all four encapsulation, decapsulation, and key-check functions. ML-DSA sigGen registers `FIPS204-tr1`, expanded keys, deterministic and randomized signing, and pure external and internal interfaces; HashML-DSA is unadvertised. RSA signatures use SHA-256/384/512, and PSS uses MGF1 with a salt as long as its hash output. RSA sigVer requests exponent 65537. Capability metadata is checked locally; a live NIST registration still needs the maintainer's credentials.

A debug build, and a release build with `--cfg rind_cpu_disable`, honours `RIND_CPU_DISABLE_<feature>`, so one process is one CPU path. `rind-fips` applies that mask as the module loads; this binary calls rind, which is where `__acvp` lives. AES-GCM with an internal IV is refused until [that quest](../quest/m4/fips/gcm-iv.md). RSA key generation is not advertised: rind has no FIPS 186-5 generation from the server's seeds or candidates.

rind's `__acvp` feature exists only for this binary. A leading `__` marks it internal, as `__ctgrind` is, and it is not a supported API. The binary enables `wipe` as well, so the decapsulation key, the shared secrets, the expanded ML-DSA private key, an ECDSA private scalar, an Ed25519 seed, the RSA primitive's output, HKDF's extracted and expanded keys, PBKDF's derived keys, unwrapped AES keys, and `hmacDRBG`'s whole state are wiped on drop. KDFs and key unwrapping fill owned wiping buffers directly. Secret replies retain their wiping allocation when moved out of a reply.

`hmacDRBG` is rind's `HmacDrbg`. The wrapper context owns the cached RSA signing keys and releases them when the context drops, including at EOF or on an error.

`admin/ctgrind` checks the secret paths this binary adds. rind's unit suite, built with `__acvp`, runs the `acvp` module's tests: the HMAC_DRBG for every hash ACVP names, seeded ML-KEM-768 key generation, encapsulation, and decapsulation of a parsed key, raw HKDF expansion, the RSA primitive's exponent at its public length (including leading zero bytes), all RSA CRT sample vectors with their private components marked secret, and ML-DSA signing with a fixed `rnd`. Both standard and CRT requests validate their public key and apply a public fault check; CRT also validates every private component. The adapter suite runs `tests/ctgrind.rs`, which marks the secret arguments `acvptool` sends for ECDH, ECDSA sigGen, hmacDRBG, HKDF and PBKDF, key wrapping, ML-KEM, ML-DSA sigGen, and the raw RSA exponent. ECDSA signing checks short, field-width, and zero-padded scalars on P-256, P-384, and P-521, and refuses a nonzero excess prefix. Valgrind is Linux-only.
